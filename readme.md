# QQ 聊天记录 .bak 文件解包指南

> 本文档是面向大众的通用指南，介绍 QQ（NTQQ，即新 QQ / QQ9x）导出的聊天记录备份文件 `.bak` 的结构、解包方法、数据库解密思路与常见坑。
> 文中不包含任何具体账号、密钥或个人数据；所有操作请只对**你自己拥有或已获得明确授权**的数据进行。

---

## 1. `.bak` 文件是什么

- QQ 客户端的"聊天记录备份/迁移"功能会生成一个 `.bak` 文件。
- 它**不是**某种私有二进制格式，而是一个 **ZIP 压缩包**：文件起始字节为 `PK`（ZIP 魔数）。
- 由于扩展名是 `.bak`，Windows 自带的 `Expand-Archive`、部分解压软件会拒绝直接打开，需要先改名为 `.zip`（操作副本，不要动原文件）。

## 2. 解包步骤（只读安全流程）

1. **复制**原始 `.bak` 到一个临时目录，把副本扩展名改为 `.zip`：
   ```powershell
   Copy-Item "聊天记录.bak" "$env:TEMP\qq.zip"
   Expand-Archive "$env:TEMP\qq.zip" "$env:TEMP\qqbak"
   ```
   也可以用 7-Zip 等工具直接打开副本。
2. **原始 `.bak` 保持不动**，后续所有操作都在副本上进行。
3. 解包后得到两个目录：

```
qqbak/
├── db/      # 若干无扩展名的数据库文件（加密的 SQLite 变体）
└── files/   # 若干无扩展名的资源文件（图片/语音等原始数据）
```

## 3. 包内内容结构

### 3.1 `db/` 目录

- 包含若干个（常见为 4 个左右）以 32 位十六进制字符串命名的文件，大小从几十 MB 到一百多 MB 不等。
- 这些就是聊天消息数据库，特征：
  - 起始字符串是 `SQLite header 3\0`（注意：**不是**标准 SQLite 的 `SQLite format 3\0`），普通 `sqlite3` 打开会报 `file is not a database`。
  - 偏移 `0x20` 附近可见 `MSG0` 字样，随后有类 protobuf 字段和一段 128 个十六进制字符的元数据。
  - 头部区域约 1024 字节（大部分为零填充），从偏移 1024 开始是高熵（加密）数据。
- **结论**：这是"腾讯自定义头部 + SQLCipher 式加密"的数据库，**不能离线直接用 sqlite3 打开**，具体见第 5 节。

### 3.2 `files/` 目录

- 若干无扩展名资源文件，是聊天中的图片、语音等原始数据。
- 通常需要结合数据库中的资源索引（文件名/md5 映射）才能对应到具体消息，一般分析文字内容时可暂不处理。

## 4. 解密路线总览

对 `.bak` 内加密库，目前有三条路线，难度和可行性差别很大：

| 路线 | 思路 | 可行性 |
| --- | --- | --- |
| A. 导入回 QQ（**推荐**） | 在登录同一账号的电脑版 QQ 里导入备份，然后用公开工具读取**本机** NTQQ 数据库 | ✅ 已验证可行，最省力 |
| B. 内存提取密钥 + 解密本机库 | 扫描正在运行的 QQ 进程内存拿到数据库密钥，再离线解密本机库 | ✅ 对本机库可行，需一定技术功底 |
| C. 离线直接解密 bak 内库 | 不经过 QQ，直接解开包内 4 个库 | ❌ 公开手段暂未打通（密钥不在本地内存，需实现腾讯密钥交换协议） |

> 结论：**先走路线 A**。除非有特殊需求，不要在路线 C 上消耗时间——bak 包内库的解密密钥不在本机 QQ 进程内存里（已实测扫描无匹配），公开社区也尚无可靠的离线解密方案。

## 5. 路线 A：导入 QQ 后读取本机库

### 5.1 操作步骤

1. 在电脑版 QQ（NTQQ）中登录**备份所属的那个账号**。
2. 使用 QQ 自带的"聊天记录备份与恢复 / 导入"功能，导入 `.bak` 文件。
3. 导入完成后，聊天数据会合入本机数据库（见 5.2）。
4. 用公开工具（见第 9 节参考项目）提取密钥并解密导出。

### 5.2 本机 NTQQ 数据库位置

```
%USERPROFILE%\Documents\Tencent Files\<QQ号>\nt_qq\nt_db\
```

常见库文件：

| 文件 | 内容 |
| --- | --- |
| `nt_msg.db` | 聊天消息主库（最大） |
| `profile_info.db` | 资料信息 |
| `group_info.db` | 群信息 |

### 5.3 本机库的格式

- 同样有 1024 字节自定义头，但标记为 `QQ_NT DB`，包含 `HMAC_SHA1` 等字段（与 bak 包内库的 `MSG0` 头不同）。
- 头部之后是 SQLCipher 式加密页。

### 5.4 备份临时库（可选参考）

导入过程中 QQ 会在下面位置生成一个**明文标准 SQLite** 的临时库：

```
...\Tencent Files\<QQ号>\nt_qq\nt_data\msgbackup\temp\<对方QQ号>_<n>.db
```

- 表结构：`msg`（消息主表）、`res`（资源）、`ex_info`（含 `key_meta`）等。
- **注意陷阱**：容器是明文 SQLite ≠ 消息正文可读。`msg` 表的 `extensionData` 列仍是加密/编码的二进制，需要额外解密才能读出内容。
- 这种临时文件随时可能被 QQ 清理，发现后应先复制再分析。

## 6. 路线 B：密钥提取与解密技术参数

以下参数为社区公开研究 + 实测验证的配置，适用于**本机 NTQQ 库**（`nt_msg.db` 等）：

### 6.1 密钥提取

- 用只读方式扫描 QQ 进程内存（`OpenProcess` + `VirtualQueryEx` + `ReadProcessMemory`），查找形如
  `x'<64位hex key><32位hex salt>'` 的字符串。
- 每个候选 key/salt 对需用第一页 HMAC 验证确认（见 6.2），验证通过才是真密钥。
- **密钥是敏感材料**：不要写入公开文档、不要上传，用完删除。

### 6.2 解密参数（实测可用）

```text
自定义头部:      1024 字节（解密前剥掉）
SQLCipher 页长:  4096 字节
首页 salt:       16 字节（取自内存扫描结果）
加密算法:        AES-256-CBC
页尾 reserve:    48 字节（IV 16 + HMAC-SHA1 20 + 补齐）
HMAC 密钥派生:   salt 每字节 XOR 0x3a → PBKDF2-HMAC-SHA512, 迭代 2 次, 输出 32 字节
页号编码:        小端
内存中的 key:    视为已派生的 AES key，不要再当口令做完整 KDF
```

### 6.3 输出重组的关键点（最容易出错的地方）

解密成功 ≠ 输出可用。逐页解密后必须正确重组，否则 SQLite 会报 `database disk image is malformed`：

1. **非首页也要补齐到 4096 字节**：每页解密后只得到 4048 字节数据区，必须补上 48 字节保留区，否则整个文件页错位。
2. **明文输出页头的保留区字段（header offset 20）应写 48（RESERVE）**，不要照抄加密库里的原始值（如 0x50），也不要写 0——写 0 会让 SQLite 按 4096 字节数据区解析，cell 指针数组全部错位。
3. 不要用"宽泛 `except` 后写零"的方式掩盖错误：校验失败、缺函数、布局错误、文件损坏要分别明确报错，否则容易生成"伪装成有 SQLite 头的全零文件"。
4. 输出文件用 `PRAGMA quick_check` 验证；只余少量 freelist 碎片警告属于无害。

## 7. 消息表结构参考（解密成功后）

以下是社区整理（参考 QQNT_Export 等项目）的 `nt_msg.db` 字段含义，具体取值建议用样本实测：

| 字段 | 含义 |
| --- | --- |
| `c2c_msg_table` | 私聊消息表 |
| `40001` | 消息 ID |
| `40003` | 消息序号 |
| `40011` / `40012` | 消息类型 / 子类型 |
| `40013` | 发送标志（发送者/接收者，需实测） |
| `40020` | 发送者 NT UID |
| `40021` | 私聊对象 NT UID |
| `40030` | 私聊对象 QQ 号 |
| `40033` | 发送者 QQ 号 |
| `40050` | Unix 秒时间戳 |
| `40090` / `40093` | 名片/昵称等 |
| `40800` | protobuf 消息体（`Elements.elements`） |
| `40900` | 转发/引用等附加内容 |

消息体内层（protobuf）常用段字段：

- `45002` 段类型；`45101` 文本；`47601`/`47602` 表情；`45923` 语音转文字；`47423` 引用段；`48214` 等为系统通知。

**重要提醒**：系统通知消息（如"戳一戳"）里的发送者字段（40020）不可靠，应按通知文本中的 `<qq uin>` 判定实际发起者。

## 8. 常见坑清单（快速自查）

- [ ] 直接用 `sqlite3` 打开 bak 内库或本机库 → 报 `file is not a database`，正常，都有自定义头。
- [ ] 解密输出报 `malformed` → 先检查**输出重组逻辑**（页长补齐、header offset 20 的 reserve 值），不要先怀疑原库损坏。
- [ ] 找不到明文 `SQLite format 3` 魔数就判定密钥无效 → 错误方法，SQLCipher 首页本来就不含明文魔数，应该用 HMAC 验证第一页。
- [ ] 把明文 SQLite 容器当成"已能读到聊天记录" → `extensionData` 等消息体仍是加密的。
- [ ] 在临时目录放自写脚本时与标准库重名（如 `inspect.py`）→ 会遮蔽 Python 标准库产生灵异错误；脚本放独立子目录。
- [ ] 引用/合并转发/系统通知里的文字被当成某人本人说的话 → 统计时需剔除。
- [ ] 图片、语音未识别 ≠ 没有表达，样本覆盖率要如实标注。
- [ ] 硬编码上一次会话的 PID、临时路径 → 每次都会变，应动态获取。

## 10. 安全与隐私注意事项

- 所有操作只对**副本**进行；原始 `.bak` 和 QQ 正在使用的数据库不要原地改写。
- 只处理自己拥有或已获得明确授权的聊天数据；不要读取、分析无关的第三方会话。
- 密钥、密钥文件、含密钥的脚本属于敏感材料：不外传、不上传、用完删除。
- 做人物分析/语料整理时注意脱敏：不写无必要的账号、住址、密钥或第三人信息；年龄、地域、职业等敏感身份只在本人明确陈述且上下文支持时记录，否则写"未知/样本不足"。
- 使用第三方开源工具前先审查代码；下载或运行公开代码不代表其可信或适配你的 QQ 版本。
- 仅用于学习使用
